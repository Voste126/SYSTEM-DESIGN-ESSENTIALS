Distributed rate limiting, performance, and wrap-up

A single-server rate limiter is the easy 20%. Two problems show up the moment you scale to multiple instances — and this is usually exactly where a senior-level interview conversation goes next.

Problem 1: the race condition

Read counter, check threshold, write counter+1 — three separate steps, not one atomic operation.

Counter currently at 3. Two requests about to arrive at the same instant.
The bug: both requests read "3" before either writes back, both compute "4," and both write "4" — the counter should be 5, but two real requests only got counted as one. The fix: not locks (too slow) — a Lua script running the whole read-check-increment sequence as one atomic unit inside Redis, or Redis's sorted-set structure, which supports this atomically by design.

Problem 2: synchronization across multiple rate-limiter instances

At real scale, one rate-limiter server isn't enough — but a stateless web tier means a client's requests can land on different instances between calls.

Client, request 1 → limiter A. Request 2 → limiter B.
The fix: not sticky sessions (not scalable, not flexible) — a shared, centralized data store (Redis again) that every rate-limiter instance reads and writes against, so there's exactly one source of truth per client regardless of which instance handled which request.

Performance and monitoring, briefly

multi-datacenter

Latency to one distant rate-limiter location can dominate response time for far-away users — route each client to its nearest edge location.

eventual consistency

Perfect real-time sync across locations isn't necessary for a system whose whole job is enforcing an approximate cap, not an exact one.

monitoring

Is the algorithm working, and are the rules well-calibrated? A flash-sale traffic spike revealing your algorithm can't handle bursts is a signal to switch toward token bucket.

Wrap-up: extra talking points worth having ready

Hard vs. soft limits: a hard limit never allows the threshold to be exceeded, even briefly; a soft limit tolerates a short grace period over it.
Rate limiting isn't only application-layer (L7/HTTP): it's equally possible at the network layer (L3) using IP-level tooling — a genuinely different mechanism from the HTTP middleware discussed throughout this chapter.
Advice for well-behaved clients: cache locally to avoid redundant calls, respect documented limits, handle rate-limit errors gracefully rather than crashing, and back off with increasing delay on retries.
