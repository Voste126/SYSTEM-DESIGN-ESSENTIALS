Token bucket and leaking bucket

Two algorithms, side by side. One tolerates bursts on purpose. The other refuses to, on purpose. Neither is "better" — they're built for opposite goals.

Token bucket

A bucket refills at a steady rate, up to a fixed capacity. Every request costs one token; no tokens left means the request is dropped. Used by Amazon and Stripe.

Bucket capacity: 4. Refill: 2/second.
Pros: simple, memory-efficient, and — the key feature — tolerates a burst gracefully, as long as tokens have accumulated. Con: tuning bucket size and refill rate correctly isn't always obvious.

Leaking bucket

A FIFO queue processed at a strictly constant output rate. A full queue drops new requests. Shopify uses this approach.

Queue capacity: 4. Outflow: 1 every 500ms.
Pros: memory-efficient, and ideal when you need a genuinely stable, predictable output rate. Con: a burst can fill the queue with a backlog of old requests — recent ones get rejected while stale ones are still processing.

Same burst, different outcome

Feed both algorithms the exact same burst of 6 requests arriving all at once. Token bucket lets through however many tokens happen to be available right then. Leaking bucket only ever processes at its fixed rate, no matter how many requests are waiting.
