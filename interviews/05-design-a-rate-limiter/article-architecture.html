Architecture, rules, and response headers

Every algorithm on the last two pages reduces to the same architecture: a fast counter, a threshold check, and a clear signal back to the client.

Why the counter lives in Redis, not a database

A request, about to hit the rate-limiting middleware.
Why Redis specifically: it natively supports exactly the two operations this needs — INCR (atomically bump a counter) and EXPIRE (auto-delete it once the time window passes) — and it's fast enough to sit on the hot path of every request, unlike a disk-backed database.

Rules: declarative, stored on disk, cached for speed

domain: messaging descriptor: message_type = marketing limit: 5 per day # translation: no more than 5 marketing # messages per user per day
domain: auth descriptor: auth_type = login limit: 5 per minute # translation: no more than 5 login # attempts per minute

Rules like these live in configuration files on disk; background workers pull them into a fast cache periodically, so the actual request path never has to touch disk directly.

What the client actually sees

A client, about to exceed its limit.
Three response headers turn "getting rate limited" into something a client can react to gracefully: remaining allowed requests, the total limit per window, and how long to wait before retrying — paired with an HTTP 429 status.
