Heap file vs. clustered index

An index's value can point at a row stored elsewhere, or be the row itself. Watch what changes when multiple secondary indexes exist.

Two secondary indexes, one row of actual data. Press a button.
The trade-off. Heap files avoid duplicating the row across every index — cheap on storage, one extra hop on reads. Clustered indexes skip that hop for the primary lookup, at the cost of duplicating (or entirely owning) the row's data. A covering index is the middle ground: store just enough extra columns that some queries never touch the underlying table at all.

Why a 2D query breaks a normal index

"Find restaurants within this map rectangle" needs a range on both latitude and longitude simultaneously. A standard B-tree or LSM-tree index can only give you an efficient range on one dimension at a time.

A latitude-only index gives you a horizontal band. A longitude-only index gives you a vertical band. Neither alone gives you the intersection.
The fix: R-trees (used by PostGIS via PostgreSQL's generalized search tree), or translating 2D coordinates into one number via a space-filling curve and using an ordinary B-tree on that. The same idea generalizes past geography — a (date, temperature) index, or a (red, green, blue) color index, solves the identical structural problem.

The rest, briefly

Concatenated (multi-column) indexes combine fields into one key by appending them, like a phone book indexed by (lastname, firstname) — great for "all Smiths" or "Smith, John," useless for "everyone named John."
Fuzzy / full-text search needs a different approach entirely: Lucene finds typo-tolerant matches by representing its term index as a finite-state automaton (like a trie) over characters, convertible into a Levenshtein automaton for efficient edit-distance search — not a sparse offset list like LevelDB uses.
In-memory databases (Redis, Memcached, VoltDB, RAMCloud) aren't fast primarily because they skip disk reads — a disk-based engine with enough RAM barely touches disk anyway, since the OS caches hot blocks. The real win is skipping the overhead of encoding data into a disk-writable format at all. Durability, when offered, comes from an on-disk change log, periodic snapshots, or replication — not from avoiding disk entirely.
