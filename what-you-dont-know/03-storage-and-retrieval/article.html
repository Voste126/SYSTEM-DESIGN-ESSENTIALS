Data structures that power your database

Appending to a file is the fastest possible write. Everything below exists to answer one question: how do you get fast reads without giving that up? Press play on each panel — these actually move.

01

The naive scan vs. the hash index jump

The simplest database is a file you only ever append to. Reading means scanning from the top until you find the last matching line — cost grows with every record you add. A hash index fixes this by remembering exactly where each key's latest value lives, so reading becomes one direct jump instead of a scan.

02

Compaction and merging

Segments fill up and get closed. Compaction throws away every value for a key except the newest one within that segment. Merging then combines several compacted segments into one — always producing a new file, since segments are never edited in place.

03

SSTables: sorted merging, mergesort-style

Once segments are sorted by key, merging two of them is exactly mergesort: always take whichever front value is smallest, advance that pointer, repeat. This works efficiently even when both files are far bigger than memory.

Why this also fixes the "must fit in memory" problem. Because the file is sorted, a sparse index — one entry every few kilobytes — is enough. Knowing the offsets of handbag and handsome tells you handiwork must be between them, without ever storing it directly.

04

The LSM-tree in motion: memtable, flush, and a Bloom filter shortcut

Writes land in an in-memory sorted tree (the memtable). Once it's full, it flushes to disk as a new SSTable. In the background, older SSTables keep merging into fewer, larger ones. A Bloom filter sits in front of the whole cascade, cheaply ruling out segments that can't possibly contain a key you're looking for.

The crash-safety detail this hides: every write also hits a separate, unsorted write-ahead log on disk immediately — its only job is rebuilding the memtable if the process crashes before a flush. Once a flush completes, that log entry is discarded.

05

Reference: real-world implementations and compaction strategies

The mechanics above are the same across every real system that uses them — what differs is which compaction strategy each one picked, and whether it's using a hash index at all or has moved to the full LSM-tree cascade.

The practical engineering checklist. Turning "a hash map of offsets" into a real, crash-safe engine takes five specific pieces: a binary file format (length-prefixed strings, no CSV escaping headaches); tombstones for deletion (a marker appended for a key, since you can't remove a line from an append-only file); crash recovery via periodic hash-map snapshots to disk (so restart doesn't mean re-scanning every segment from scratch); checksums to detect and skip partially-written records from a mid-write crash; and a single writer thread with immutable finished segments, so concurrent reads need zero coordination.

Where the names come from. "SSTable" and "memtable" both originate in Google's Bigtable paper — LevelDB, RocksDB, Cassandra, and HBase all trace back to that same lineage despite being separate projects. The technique itself was formally named the Log-Structured Merge-Tree (LSM-Tree) by Patrick O'Neil and colleagues, predating every specific system in the table above.
