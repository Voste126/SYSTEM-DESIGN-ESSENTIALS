Dataflow through databases

The simplest possible case: writing to a database is sending a message to your future self. That framing makes both compatibility directions, and one very avoidable data-loss trap, easy to see.

Writing is encoding, reading later is decoding

If the same process writes and later reads its own data, storing something in a database is exactly like sending a message forward in time to yourself.

A value, about to be written today and read next year.
Why both directions matter here: backward compatibility is obvious (future-you must read past-you's writes). But databases are almost always accessed by many processes at once — some mid-upgrade, some not — so forward compatibility (old code reading new code's writes) is just as necessary, for a completely different reason: concurrent versions, not time travel.

The trap: a round trip through a model object can silently drop a field

New code writes a record including a new field. Old code reads it, changes something unrelated, and writes it back. The field should survive that round trip — but it doesn't always.

A record, written by new code, about to be touched by old code.
Where it actually breaks: not at the encoding level — most formats preserve unknown fields on the wire just fine. It breaks when old code decodes the record into an in-memory model object that has no slot for the unknown field, edits that object, and re-encodes the object rather than the original bytes. The field was never lost by the format; it was lost because the in-memory representation had nowhere to keep it.

"Data outlives code"

A deploy can replace an entire server-side codebase within minutes. A database's contents don't get that luxury — five-year-old rows, written under a five-year-old schema, are often still sitting there untouched.

One table, rows written at very different times.
Why full rewrites are rare: migrating a large existing dataset into a new schema is possible but expensive, so most systems avoid it. Simple changes — like adding a nullable column — sidestep the problem entirely: old rows are just treated as having null for a column that didn't exist yet when they were written.

Archival storage: the one case where you get to cheat

A backup or warehouse-bound snapshot doesn't have to preserve historical schema mixing — since you're rewriting the data anyway, you can normalize everything to the latest schema on the way out, producing an internally consistent dump even from a messy live source. Since the dump is written once and never modified again, an immutable format like Avro's object container files fits naturally — and it's a convenient moment to switch to an analytics-friendly column-oriented layout too.
