Data encoding, evolution, and versioning for RPC

RPC gets one genuine simplification databases don't. It also gets one problem that's uniquely painful: a provider that can't force its own clients to upgrade.

The simplification: servers upgrade first, always

For dataflow through services, it's reasonable to assume servers get updated before their clients. That narrows the requirement compared to databases, which need both directions, all the time.

A service and its clients, about to upgrade in the expected order.
What this actually buys you: you only need backward compatibility on requests (a server has to handle older clients' requests) and forward compatibility on responses (an older client has to handle a newer server's responses) — not the full "both directions, always" requirement databases face.

Where the compatibility rules actually come from

Thrift, gRPC (protobuf), Avro RPC — inherit whatever compatibility rules their underlying encoding already has (the field-tag rules from earlier in this chapter, for the first two).
SOAP — requests/responses are XML-schema-defined; schemas can evolve, with some known subtle pitfalls.
RESTful JSON APIs — usually no formally specified schema at all; adding new optional request parameters, and adding new fields to response objects, are both generally treated as compatible changes in practice.

Why cross-organizational RPC is uniquely hard

A service provider frequently has zero control over its own clients, especially once an API is public — it can't force anyone to upgrade on any schedule. Compatibility sometimes has to hold indefinitely.

A breaking API change, and clients stuck on the old version.

How a client signals which version it wants — there's no single standard

GET /v2/users/42 HTTP/1.1 # simple, visible, easy to route on the server side # but "leaks" versioning into every URL a client hardcodes
GET /users/42 HTTP/1.1 Accept: application/vnd.example.v2+json # keeps the URL clean # less visible, easy to forget to set explicitly
API key abc123 → server-side record: "wants v2" # version is set once via an admin interface, not per-request # useful when clients can't easily change request-time headers
