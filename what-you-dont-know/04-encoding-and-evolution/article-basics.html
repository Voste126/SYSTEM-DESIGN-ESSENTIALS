What "encoding" actually means

Old code, new code, old data, new data — all coexisting at once, and everything still has to work. This page covers why that's true, and why your language's built-in save/load feature is a trap for anything long-lived.

Why old and new code have to coexist

A server-side rolling upgrade deploys a new version to a few machines at a time, watching for problems before continuing — which means old and new versions run side by side for a while, on purpose. Client-side apps are worse: a user might not update for months. Either way, your system has to keep working with a mix of old and new code, and old and new data, at the same time.

Five servers, about to be upgraded two at a time.
Backward compatibility: newer code can read data written by older code. Forward compatibility: older code can read data written by newer code — the harder direction, since old code has to gracefully ignore things it's never seen.

Encoding and decoding, in one animation

In memory, data is objects and pointers — fast for the CPU, meaningless to any other process. To save or send it, you flatten it into a self-contained sequence of bytes: encoding. Reversing that is decoding.

An in-memory object, about to cross a process boundary.

Why your language's built-in serializer is a trap

Java's Serializable, Python's pickle, Ruby's Marshal — all convenient, all carrying the same four problems.

Decoding untrusted bytes with a language-native deserializer.
The four problems, in short: lock-in (tied to one language, forever); security (decoding often means instantiating arbitrary classes — a real, documented path to remote code execution if an attacker controls the bytes); versioning as an afterthought (not built with backward/forward compatibility in mind); poor performance (Java's built-in serialization is a frequently-cited example of both slow and bloated). The practical rule: don't use these for anything beyond short-lived, throwaway data.
