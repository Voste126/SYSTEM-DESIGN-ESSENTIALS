Binary encodings: MessagePack, Thrift, Protocol Buffers

Same tiny record, encoded four different ways. Watch the byte count shrink as each format adds a bit more structure — and see exactly where those savings come from.

The record we'll encode, all the way through this page

{ userName: "Martin", favoriteNumber: 1337, interests: ["daydreaming", "hacking"] }

MessagePack: binary, but still no schema

MessagePack keeps JSON's data model exactly as-is, just encoded as bytes instead of text. Since there's still no schema anywhere, every field name has to be spelled out, literally, inside the encoded bytes.

Press play to watch the encoder tag and spell out each field.
Result: 66 bytes — barely smaller than the 81-byte plain-text JSON version. The field names (userName, favoriteNumber, interests) are sitting right there in the bytes, spelled out in full, every single time this record gets encoded.

Thrift and Protocol Buffers: add a schema, drop the field names

Both define the schema separately, ahead of time, giving each field a small integer tag instead of relying on its name. The encoded bytes then only need to contain the tag number — the schema (which both sides already have) is what maps tag 1 back to userName.

Same record, no field names anywhere in the bytes.
required vs. optional changes nothing about the actual bytes on the wire — there's no "required" marker in the encoding at all. The only difference is a runtime check: a required field gets validated as present after decoding, which is a code-level guarantee, not a wire-format one.

Same record, five encodings. Watch where the size actually comes from.
Where the savings come from, concretely: CompactProtocol and Protocol Buffers both pack a field's type and tag into a single byte, and use variable-length integers — small numbers like 1337 take just two bytes instead of a fixed eight, using the top bit of each byte to say "more bytes follow." Combined with dropping field names entirely, that's the whole story behind going from 66 bytes down to 33.
