Field tags: how schema evolution actually works

Four rules, each demonstrated by watching old and new code actually try to read each other's data. This page is the payoff for everything on pages 1-3.

Rule 1 — renaming a field is always safe

The encoded bytes never contain field names, only tag numbers. Renaming userName to user_name in the schema changes nothing about data already encoded.

Old data, encoded under the original field name.

Rule 2 — adding an optional field is forward-compatible

New code adds field 4, phoneNumber. Old code has never heard of tag 4 — what does it do when it sees data written by the new code?

New code just wrote a record including tag 4.
Why this works: every field carries a type annotation, so even code that's never heard of tag 4 knows exactly how many bytes to skip — it just ignores what it doesn't recognize and moves on.

Rule 3 — new fields must be optional, never required

What happens when new code — expecting field 4 to always be present, because it was marked required — reads data written by old code, before field 4 existed at all?

Old data, written before field 4 existed.

Rule 4 — you can never reuse a retired tag number

Say tag 2 (favoriteNumber) gets removed, and a year later someone reuses tag 2 for a brand-new, unrelated field.

Old data, still sitting on disk somewhere, still tagged 2.
Why this breaks: old data encoded under tag 2 as a number gets misread as the new field's type entirely — the tag number is the only thing tying bytes to meaning, and reusing it erases that link for every piece of old data still floating around the system.

The four rules, as a quick reference

Safe, always: renaming a field in the schema.
Safe for forward compatibility: adding a new field with a brand-new tag number — old code skips it.
Safe for backward compatibility: adding a new field, as long as it's optional or has a default — never required.
Never safe: changing an existing field's tag number, or reusing a retired tag number for something new.

Notes from Designing Data-Intensive Applications, ch. 4 — Martin Kleppmann. This closes out part 1 of the chapter; JSON-based schema formats like Avro, and the modes of dataflow (REST, RPC, message queues), are a separate future addition.
