The subtle problems with JSON, XML, and CSV

These formats are genuinely good enough for a lot of real use — but "good enough" hides two sharp edges worth seeing directly rather than just being told about.

Sharp edge 1: big numbers silently lose precision

JSON tells strings and numbers apart, but never distinguishes integers from floating-point, and specifies no precision. JavaScript stores every JSON number as a 64-bit float — which can only represent integers exactly up to about 9 quadrillion (2^53). Past that, things quietly go wrong.

A 64-bit ID, about to be parsed by a JavaScript JSON parser.
Twitter's actual fix: every tweet ID appears twice in API responses — once as a plain JSON number (which a JS client will mangle) and once as a string (which won't). Not elegant, but it works.

Sharp edge 2: no native way to store raw bytes

JSON and XML handle human-readable text beautifully but have no way to represent an arbitrary sequence of bytes that isn't text — an image thumbnail, a binary file. The workaround: Base64-encode the bytes into a text string.

Raw binary data, about to be encoded as text.
The cost: Base64 inflates the data by about 33% — and you still need a schema somewhere to say "by the way, this field is Base64, decode it back to bytes before use," since nothing in plain JSON marks that on its own.

Reference: where each format actually stands

JSON — distinguishes strings from numbers, not integers from floats; no binary support; schema optional and often skipped entirely.
XML — can't tell numbers from digit-strings without an external schema; no binary support either; has a more mature (if complex) schema ecosystem than JSON.
CSV — essentially no schema at all; your application defines what every column means; escaping rules for commas/newlines are formally specified, but not every parser actually implements them correctly.
