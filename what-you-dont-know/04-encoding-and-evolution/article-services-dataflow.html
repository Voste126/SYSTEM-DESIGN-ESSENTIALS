Dataflow through services: REST and SOAP

A service is an API a server exposes; clients call it. Two philosophies for how to build that API turn out to barely agree on anything.

Client, server, and the service in between

A mobile app, a service, and that service's own downstream dependency.
Services vs. databases: both let a caller submit and query data, but a database accepts arbitrary queries via a general-purpose language, while a service only accepts the specific inputs its own business logic predetermined — real encapsulation a raw database interface doesn't offer.

REST vs. SOAP: two philosophies, side by side

REST isn't a protocol — it's a design style built directly on HTTP's own features. SOAP is the opposite instinct: XML-based, technically HTTP-agnostic, layered with its own standards instead of using HTTP's.

GET /users/42 HTTP/1.1 Host: api.example.com Accept: application/json --- response --- {"id": 42, "name": "Martin"} # uses HTTP verbs, URLs, and headers directly. # readable with a browser or curl, no tooling needed.
POST /UserService HTTP/1.1 Content-Type: text/xml <soap:Envelope> <soap:Body> <GetUserRequest> <UserId>42</UserId> </GetUserRequest> </soap:Body> </soap:Envelope> # HTTP is just a transport here — SOAP avoids using # most of its native features, uses its own WS-* standards instead. # described by WSDL (not human-readable); needs code generation # and heavy tooling to use in practice.
Why REST pulled ahead, especially across organizations: simpler tooling requirements, no code-generation dependency, and — despite SOAP being nominally standardized — real interoperability friction between different vendors' SOAP implementations in practice. REST APIs are typically documented with OpenAPI/Swagger rather than WSDL.
