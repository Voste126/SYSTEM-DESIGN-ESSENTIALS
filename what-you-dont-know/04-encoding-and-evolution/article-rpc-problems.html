The problems with RPC

RPC's whole promise is making a network call feel like calling a local function. Two animations below show exactly why that promise can't actually be kept.

Local calls are predictable. Network calls have a fourth outcome.

A local function call succeeds, throws, or (rarely) never returns. A network call has a possibility neither of those has: it can time out with no way to know what actually happened on the other end.

A request, about to hit an unpredictable network.
The genuinely hard part: you don't know if the request never arrived, or if it arrived and was processed but the response got lost on the way back. Those two situations call for opposite responses, and from the caller's side, they're indistinguishable.

Retrying a "failed" request can duplicate a real action

If you retry after a timeout, and it turns out the original request actually went through, you've now told the server to do the same thing twice — something a local function call structurally cannot do to itself.

"Charge $50" — about to be retried after an apparent timeout.
The fix isn't automatic: avoiding this requires deliberately building deduplication (idempotence) into the protocol — tagging each request with a unique ID the server can recognize as "already handled," so a retry is safe rather than repeating the action.

The rest of the list, briefly

  • Latency is wildly less predictable. A local call takes roughly the same time every time; a network call can be sub-millisecond one moment and many seconds the next, for the exact same request, depending on network and remote-service conditions entirely outside your control.
  • You can't just pass a pointer. A local call hands over a reference to memory already sitting there. A network call has to encode every parameter into bytes first — fine for small values, increasingly awkward as objects grow larger or more complex.
  • Cross-language type mismatches. If client and server are different languages, the framework has to translate types between them — and languages don't all agree on what types exist (the large-integer precision issue from earlier in this chapter is a direct instance of exactly this problem).
The conclusion this leads to: don't try to disguise a network call as a local one. Part of REST's appeal is that it never pretends otherwise — even though people still build RPC-style libraries on top of REST anyway.

Notes from Designing Data-Intensive Applications, ch. 4 — Martin Kleppmann. Continue to page 8 for how modern RPC frameworks respond to these exact problems.
