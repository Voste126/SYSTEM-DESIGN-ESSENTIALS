senior engineer track — chapter 02

Relational vs. document models

Same résumé, two shapes. Toggle below to see exactly why one-to-many loves documents and many-to-many hates them.

01

Same data, two shapes

Every layer of an application translates data into a simpler model for the layer below it. Real-world things become objects in your code; objects become a general-purpose model — tables, JSON, or graphs — before they ever touch a disk. This chapter is entirely about that one layer: which general-purpose shape should your data take?

Toggle the diagram on the left. Same résumé, same information — one version splits it into four linked tables, the other nests it as one tree. Neither is "correct"; they're optimized for different relationship shapes.

02

One-to-many loves trees. Many-to-many hates them.

A résumé's jobs and education are a clean one-to-many relationship — one person, many positions — which is exactly what a nested document represents naturally. The moment you add a feature like "link each job to a company page" or "let one user recommend another," you've introduced a many-to-many relationship, and now the document model needs references resolved at read time — which is a join in every way except name.

The locality tradeoff. A document is one continuous blob, so reading a whole profile is one query. But that only pays off if you actually need the whole document at once — the database still loads all of it even for a tiny read, and most writes rewrite the entire thing rather than just the changed field.

03

This exact fight happened in the 1970s

IBM's hierarchical model (IMS, 1968) stored everything as nested trees — structurally the same shape as a document database today. It handled one-to-many beautifully and many-to-many terribly, same as now. The network model (CODASYL) fixed many-to-many by letting records have multiple parents, but the cost was brutal: finding data meant manually following a specific chain of pointers — an "access path" — that a programmer had to memorize and rewrite by hand every time the data's shape changed.

The relational model won by throwing access paths out entirely. You declare what you want; a query optimizer — built once, by the database vendor — figures out how to get it, and adapts automatically as your data and indexes change. That's the actual reason relational databases dominated for 30 years: not that tables beat trees, but that "ask a question, let the system route it" beats "memorize the route yourself" once a system gets complex.

Document databases never inherited CODASYL's pointer-chasing fix for many-to-many. They resolve it exactly like relational databases do — an ID, followed up at read time — they just call it a "document reference" instead of a "foreign key."

04

Who enforces the shape, and when

Relational databases are schema-on-write: the structure is explicit, and the database rejects anything that doesn't fit at write time. Document databases are typically schema-on-read: there's no enforced structure at all — the code that later reads the data just assumes some shape and handles it if that assumption breaks. It's the same philosophical split as static vs. dynamic typing, and neither is universally right.

Here's the same migration — splitting a full name into first/last — done both ways:

ALTER TABLE users ADD COLUMN first_name text; UPDATE users SET first_name = split_part(name, ' ', 1); -- fast in Postgres (milliseconds) -- MySQL copies the whole table: can be minutes to hours
if (user && user.name && !user.first_name) { // docs written before this change don't have first_name user.first_name = user.name.split(" ")[0]; } // no migration step — the fix lives in read-time code instead

Neither approach is free — schema-on-write pays the cost up front as a migration; schema-on-read defers it into scattered conditional checks that live in the codebase indefinitely.
