senior engineer track — chapter 02

Data models and query languages

Same résumé, two shapes. Toggle below to see exactly why one-to-many loves documents and many-to-many hates them.

01

Same data, two shapes

Every layer of an application translates data into a simpler model for the layer below it. Real-world things become objects in your code; objects become a general-purpose model — tables, JSON, or graphs — before they ever touch a disk. This chapter is entirely about that one layer: which general-purpose shape should your data take?

Toggle the diagram on the left. Same résumé, same information — one version splits it into four linked tables, the other nests it as one tree. Neither is "correct"; they're optimized for different relationship shapes.

02

One-to-many loves trees. Many-to-many hates them.

A résumé's jobs and education are a clean one-to-many relationship — one person, many positions — which is exactly what a nested document represents naturally. The moment you add a feature like "link each job to a company page" or "let one user recommend another," you've introduced a many-to-many relationship, and now the document model needs references resolved at read time — which is a join in every way except name.

The locality tradeoff. A document is one continuous blob, so reading a whole profile is one query. But that only pays off if you actually need the whole document at once — the database still loads all of it even for a tiny read, and most writes rewrite the entire thing rather than just the changed field.

03

This exact fight happened in the 1970s

IBM's hierarchical model (IMS, 1968) stored everything as nested trees — structurally the same shape as a document database today. It handled one-to-many beautifully and many-to-many terribly, same as now. The network model (CODASYL) fixed many-to-many by letting records have multiple parents, but the cost was brutal: finding data meant manually following a specific chain of pointers — an "access path" — that a programmer had to memorize and rewrite by hand every time the data's shape changed.

The relational model won by throwing access paths out entirely. You declare what you want; a query optimizer — built once, by the database vendor — figures out how to get it, and adapts automatically as your data and indexes change. That's the actual reason relational databases dominated for 30 years: not that tables beat trees, but that "ask a question, let the system route it" beats "memorize the route yourself" once a system gets complex.

Document databases never inherited CODASYL's pointer-chasing fix for many-to-many. They resolve it exactly like relational databases do — an ID, followed up at read time — they just call it a "document reference" instead of a "foreign key."

04

Who enforces the shape, and when

Relational databases are schema-on-write: the structure is explicit, and the database rejects anything that doesn't fit at write time. Document databases are typically schema-on-read: there's no enforced structure at all — the code that later reads the data just assumes some shape and handles it if that assumption breaks. It's the same philosophical split as static vs. dynamic typing, and neither is universally right.

Here's the same migration — splitting a full name into first/last — done both ways:

ALTER TABLE users ADD COLUMN first_name text; UPDATE users SET first_name = split_part(name, ' ', 1); -- fast in Postgres (milliseconds) -- MySQL copies the whole table: can be minutes to hours
if (user && user.name && !user.first_name) { // docs written before this change don't have first_name user.first_name = user.name.split(" ")[0]; } // no migration step — the fix lives in read-time code instead

Neither approach is free — schema-on-write pays the cost up front as a migration; schema-on-read defers it into scattered conditional checks that live in the codebase indefinitely.

05

Declarative vs. imperative, in code

Imperative code is a recipe — do this, then this, in order. Declarative code is an order form: "bring me all the sharks," with no opinion on how the kitchen finds them. That's the entire distinction, and it's why the database is free to reorganize storage or run parts of your query in parallel without ever breaking your code — you never told it how, so it's free to change how.

SELECT * FROM animals WHERE family = 'Sharks'; -- says WHAT you want. -- doesn't care about row order, -- so the database is free to -- reorganize storage, use any -- index, or run this in parallel.
function getSharks() { var sharks = []; for (var i = 0; i < animals.length; i++) { if (animals[i].family === "Sharks") { sharks.push(animals[i]); } } return sharks; } // says exactly HOW to get it. // assumes a specific array order — // the database can never safely // change storage layout underneath // code shaped like this.
Same idea in a browser. CSS (li.selected > p { background: blue; }) keeps holding true automatically as the page changes — remove the class, the blue disappears, no extra code. The equivalent hand-written DOM-manipulation JavaScript has to be manually rerun on every state change, and if you forget, it silently goes stale.

06

MapReduce: declarative's imperative cousin

MapReduce sits between the two. You write a map function (called once per record, emits a key/value pair) and a reduce function (called once per unique key, combining everything emitted under it) — the framework calls both repeatedly for you. Counting shark sightings per month: map looks at one observation and emits ("2013-12", numAnimals); reduce sums every value that arrived under that same month key.

Writing two coordinated JavaScript functions is usually more work than one SQL-shaped query — which is exactly why MongoDB later added a fully declarative aggregation pipeline on top. A NoSQL system reinventing a JSON-flavored subset of SQL isn't a coincidence; declarative querying keeps winning for the same optimizer-freedom reason, every time.

07

When relationships stop being predictable: graphs

Lucy was born in Idaho, which is within the USA, which is within North America. She lives in London, within the UK, within Europe. Nothing here is deeply nested (document model) or a fixed number of joins (relational) — it's a chain of "within" relationships of unknown length, and that's exactly the shape graphs are built for.

08

The same query, four languages

"Find people born in the US who now live in Europe" — the exact same question, expressed in four different query languages. Watch what happens to the line count once the underlying model stops matching the question naturally.

MATCH (person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (us:Location {name:'United States'}), (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (eu:Location {name:'Europe'}) RETURN person.name
SELECT ?personName WHERE { ?person :name ?personName. ?person :bornIn / :within* / :name "United States". ?person :livesIn / :within* / :name "Europe". }
within_recursive(Loc, Name) :- name(Loc, Name). within_recursive(Loc, Name) :- within(Loc, Via), within_recursive(Via, Name). migrated(Name, Born, Living) :- name(P, Name), born_in(P, B), within_recursive(B, Born), lives_in(P, L), within_recursive(L, Living). ?- migrated(Who, 'United States', 'Europe').
WITH RECURSIVE in_usa(vertex_id) AS ( SELECT vertex_id FROM vertices WHERE properties->>'name' = 'United States' UNION SELECT edges.tail_vertex FROM edges JOIN in_usa ON edges.head_vertex = in_usa.vertex_id WHERE edges.label = 'within' ), in_europe(vertex_id) AS ( /* ...same pattern, ~6 more lines... */ ), born_in_usa(vertex_id) AS ( /* ...join through in_usa... */ ), lives_in_europe(vertex_id) AS ( /* ...join through in_europe... */ ) SELECT vertices.properties->>'name' FROM vertices JOIN born_in_usa ON vertices.vertex_id = born_in_usa.vertex_id JOIN lives_in_europe ON vertices.vertex_id = lives_in_europe.vertex_id; -- full version runs ~29 lines

This isn't "SQL is worse" — it's proof that a query language's shape follows from the data model it was built around. SQL wasn't designed to express "follow this edge zero or more times"; graph languages were.
