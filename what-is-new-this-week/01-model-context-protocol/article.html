emerging tech track — module 01

Model Context Protocol (MCP)

LSP for generative AI. How standardizing Tools, Resources, and Prompts over JSON-RPC 2.0 solves the N × M integration bottleneck.

01

The N × M integration problem

Before standard language protocols, supporting 20 languages across 20 code editors required writing 400 bespoke plugins. Microsoft solved this in 2016 with the Language Server Protocol (LSP). The Model Context Protocol (MCP) applies the exact same structural solution to generative AI agents.

Without an open standard, every agent runtime (Claude Desktop, Cursor, LangChain) must write custom connectors for every enterprise data source (Postgres, GitHub, Slack, Datadog). MCP standardizes the wire contract so an enterprise tool written once works across every agent host.

The core equation: Instead of $N \text{ hosts} \times M \text{ integrations}$, MCP creates $N \text{ hosts} + M \text{ servers}$. An enterprise only writes the server once.

02

Host-Client-Server Topology

MCP strictly enforces three separate responsibility zones:

  • Host: The top-level orchestrator. Holds the foundational model API keys, manages the user interface, and enforces the security boundary. The host decides what enters the context window.
  • Client: An in-process entity inside the host maintaining a strict 1:1 transport connection to a single server.
  • Server: An isolated process (either local subprocess or remote service) exposing enterprise context and capabilities. The server has zero direct connection to the LLM and never touches the host's model tokens.

03

JSON-RPC 2.0 & Handshake Lifecycle

Communication is strictly bi-directional JSON-RPC 2.0 over standard I/O (local stdio) or HTTP Server-Sent Events (SSE). Before any business requests can execute, both sides negotiate capabilities:

// 1. Client -> Server: initialize { "jsonrpc": "2.0", "id": 1, "method": "initialize", "params": { "protocolVersion": "2024-11-05", "capabilities": { "roots": { "listChanged": true } }, "clientInfo": { "name": "AgentRunner", "version": "1.0.0" } } } // 2. Server -> Client: capabilities result { "jsonrpc": "2.0", "id": 1, "result": { "capabilities": { "tools": { "listChanged": true }, "resources": { "subscribe": true } }, "serverInfo": { "name": "pg-mcp", "version": "0.1.0" } } } // 3. Client -> Server: notifications/initialized { "jsonrpc": "2.0", "method": "notifications/initialized" }

04

The Three Primitives: Tools, Resources, Prompts

All server capabilities map directly into three distinct primitives:

  • Tools (Active): Callable functions with strict JSON Schemas. When an LLM triggers a tool, the client sends tools/call and receives formatted results.
  • Resources (Passive): Read-only documents and data identified by standardized URIs (postgres://customers/schema). Safe for context hydration without side-effects.
  • Prompts (Workflows): Server-managed prompt templates with argument validation to standardize enterprise tasks.
Strict JSON Schemas matter: If tool arguments are loosely typed, the LLM will hallucinate parameters and trigger cascade failure loops. Strict schema definition is a production requirement.

05

Security, HITL Gates & Credential Isolation

Connecting LLMs to live databases creates severe operational risk. MCP's architecture enforces three crucial defenses:

  • Credential Isolation: Enterprise database passwords remain isolated inside the server process. The LLM host never inspects the raw credentials.
  • Human-In-The-Loop (HITL): A tool request generated by an LLM is an untrusted intent. The host must gate destructive calls behind explicit user approvals or policy engines.
  • Indirect Prompt Injection Defense: Data read via Resources is strictly passive context. Malicious commands embedded in documents cannot directly execute tools without passing through the host's policy filters.
